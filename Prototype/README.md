# iPhone guest on an iPhone host

The first milestone is a boot log from an iOS guest on an iPhone running a development build of UTM. The target is the `vresearch101` machine from vphone-linux. Stock UTM lacks that machine. The tools in this directory run on the Mac and prepare inputs for the port.

1. Cache the iPhone and cloudOS IPSWs with `python3 Prototype/cache_firmware.py --cache /path/to/cache --iphone-url HTTPS_URL --cloudos-url HTTPS_URL`. Pass the printed paths to vphone-cli's firmware preparation in place of its download URLs. Use its existing restore and patch workflow to create a disposable VM bundle. See [vphone-linux firmware preparation](https://github.com/YahiaAngelo/vphone-linux/blob/main/docs/CREATE-ON-LINUX.md).
2. Run `python3 Prototype/vphone_boot_plan.py /path/to/disposable-bundle`. It reads the configuration and checks that the two ROMs, disk, NVRAM and SEP storage are present. It prints an argument array and never executes it. The initial values of two CPUs and 3 GiB are trial settings. The Linux reference uses eight CPUs and 8 GiB. Use a separate bundle for every running VM, because the firmware and the PCI devices access the same backing files and the upstream configuration disables file locking.
3. Port the boot path into UTM's Darwin QEMU or port UTM's iOS library interface onto the pinned [vphone QEMU revision](https://github.com/YahiaAngelo/qemu-vphone/tree/14c9913d2231080bd234c69421ed4f293a25f767). UTM's dependency builder accepts a custom QEMU tree with `-q`, but the pinned vphone tree lacks UTM's shared-library build and ARM64 threaded interpreter options. Its `qemu_init(argc, argv)` also differs from UTM's three-argument loader interface. Prefer starting from UTM's QEMU and transplanting the guest hardware support to preserve both iOS targets. The headless path needs the machine, Apple CPU support, SEP and storage devices. Wire the serial output into UTM and start with the development JIT target. Add display and touch after observing the guest boot. Then run the same guest in the SE target and compare.

For storage, keep the two source archives on the preparation host. Transfer only the boot ROMs and the state required at runtime. Validate copy-on-write on a disposable VM before offering multiple profiles. Both the firmware and PCI paths need to see the same disk view, and each profile must retain the corresponding NVRAM and SEP state.
